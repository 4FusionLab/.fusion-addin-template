# Разработка аддонов 4FusionLab

[English](DEVELOPMENT.md)

## Архитектура

- `<Product>/<Product>.py`: точка входа Autodesk Fusion, жизненный цикл команд и событий. Модуль импортирует `adsk`, поэтому **не импортируйте его в автономных модульных тестах**.
- `<Product>/config.py`: стабильный идентификатор команды и метаданные продукта. Создаётся один раз.
- `<Product>/core.py`: обычный Python, независимо тестируемые вычисления и предметная логика.
- `<Product>/<Product>.manifest`: метаданные аддона Autodesk Fusion; сборщик релиза записывает вычисленную версию в ZIP, не меняя рабочий каталог.
- `scripts/build.py`: детерминированный архив, SHA-256, защита от секретов и символических ссылок.
- `.github/release-paths.txt`: проверенный перечень файлов, влияющих на поставляемые компоненты.

## Работа над новым продуктом

1. Создайте репозиторий из шаблона GitHub. Исходный шаблон намеренно нельзя публиковать.
2. Запустите **Actions → Initialize add-in** в `main`. Этот workflow недоступен в самом шаблоне и удаляет себя из созданного проекта. Он создаёт UUID манифеста и идентификатор команды для проекта.
3. Инициализатор отправляет созданный коммит со встроенным токеном GitHub; такой push **не** запускает автоматически другие workflows для push. Для проверки проекта без выпуска релиза он явно запускает workflow CI с доступом только на чтение.
4. При локальной инициализации выполните `python scripts/init_addin.py --name MyAddin --repo 4FusionLab/MyAddin`, `python scripts/check_project.py` и тесты, затем отправьте изменения в репозиторий.
5. Реализуйте команду. Все вызовы Fusion API выполняйте в соответствующем потоке Fusion и отделяйте от чистых вычислений. Добавьте тесты и результаты приёмки в Fusion.
6. При изменении поставляемых файлов выполните push в `main` или объедините PR. Успешный CI и подходящий путь исполняемого файла автоматически публикуют стабильный GitHub Release с версией.
7. Не создавайте прямые релизы для изменений только документации, тестов, CI или политик. Не создавайте теги вручную.

## Локальная проверка

```bash
python scripts/check_project.py
python -m unittest discover -s tests -v
python scripts/build.py --version 0.1.0
```

Неинициализированный исходный шаблон можно тестировать с `--allow-template`, но он **не может** публиковаться; новые продукты не должны использовать этот флаг в сценариях релиза.

## Установка в Fusion

1. Скачайте ZIP из GitHub Releases продукта или соберите его локально.
2. Распакуйте его так, чтобы каталог Fusion API AddIns содержал `<Product>/<Product>.manifest` и `<Product>/<Product>.py`. Не устанавливайте ZIP с двойной вложенностью каталогов.
3. Откройте Autodesk Fusion, перейдите в **Utilities → Add-Ins** и запустите аддон. Проверьте запись аддона на панели SOLID **ADD-INS**.
4. Запустите стартовую команду. Она должна показать сообщение и **не должна изменять модель**. Отключите аддон и убедитесь, что команда и элемент управления исчезли.
5. Повторите на macOS и Windows для зависимостей, геометрии и интерфейса, специфичных для ОС, отмечая различия. Не утверждайте, что CI выполнил приёмку в Fusion.

## Контрольный список приёмки в Fusion

- Установка, запуск, остановка и повторный запуск без дублирующихся элементов управления и утечек обработчиков.
- Команда открывается, отменяется и выполняется; результат корректен и безопасен.
- Переключение активного документа, отсутствие документа и удаление модели не приводят к небезопасной записи.
- Где применимо, проверьте параметрическое и прямое моделирование, обновление таймлайна, единицы, отмену и повтор действий.
- Взаимодействия с CAD API, порядок событий интерфейса, жизненный цикл предпросмотра и производительность проверены внутри Fusion.
- ZIP релиза содержит корректный манифест, согласованную с GitVersion версию и контрольную сумму.
- Проверьте переносимость между ОС, нативные зависимости и необходимую подпись.
- Поддерживайте точность документации EN/RU и публикуйте реальные ограничения.
